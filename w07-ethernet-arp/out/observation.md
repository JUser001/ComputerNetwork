# Week 7 · Observation

## Task 1 · Learning switch

**Why never back out the arrival port?** The destination is reachable *through* the port the frame came from, so sending it back puts a copy on a segment that already has it: hosts there see a duplicate, and the sender sees its own frame. In a topology with two switches joined by two links it is worse: each switch floods the frame back to the other, every pass makes more copies, and the network melts in a broadcast storm. (Rule 2 only stops the trivial ping-pong; real loops also need spanning tree.)

**Why flood, while a router drops?** A MAC address carries no location, and a switch is configured with nothing. But everything it serves is one broadcast domain, so if the destination exists at all it is somewhere here, and flooding is guaranteed to reach it. The reply then teaches the switch where it is. A router has a table that is meant to cover every reachable prefix, so "no route" means the destination is unreachable. Flooding across the Internet would multiply packets at every hop and cannot scale. Drop (and ICMP unreachable) is the correct answer there.

**What does aging by timeout lose?** The switch cannot tell "quiet" from "gone". A host silent for over 300 s is forgotten and its next frame is flooded (waste, still correct). A host that has left or moved stays "known" for up to 300 s, and frames for it go to a dead port until it speaks again. The more direct signal is a topology event: link-down on a port (flush everything learned there), or an explicit move notice (a gratuitous ARP, or a spanning-tree topology change that shortens aging). That is evidence of departure, not an inference from silence.

## Task 2 · Watch ARP happen

Captured on my own Windows 11 laptop, Wi-Fi interface 192.168.0.12 (MAC 4c:49:6c:11:94:f0), gateway 192.168.0.1 (88:36:6c:b2:c1:78). The capture (`arp.pcapng`, filter `arp`) holds 35 frames over 439 s.

**A2 · first entry back, and why:** The **default gateway, 192.168.0.1**. After I flushed the cache, the first ARP request my own machine sent is a broadcast "who has 192.168.0.1? tell 192.168.0.12" (packet 9, t = 102.144 s), answered 10 ms later (packet 10). The gateway is the next hop for everything that leaves the subnet (my ping and the `curl` to korea.ac.kr both go through it), so without its MAC the machine cannot send a single off-subnet packet. Nothing else was resolved: that was the only request my PC sent in the whole capture.

**A3 · entries after vs before:** `before` has **19** entries over three interfaces (2 dynamic, 17 static); `after` has **9** (1 dynamic, 8 static). On the Wi-Fi interface it is 7 → 5. The only entry ARP actually *re-learned* is the gateway. The dynamic neighbour 172.19.23.111 (a `00-15-5d` Hyper-V/WSL virtual host on the 172.19.16.1 interface) disappeared and did not come back, because nothing talked to it after the flush. The "static" rows are not learned by ARP at all: they are OS-made mappings for broadcast (`ff-ff-ff-ff-ff-ff`) and multicast addresses (`01-00-5e-...`). Several of them vanished with the flush (e.g. 192.168.0.255, 255.255.255.255) and only some came back (224.0.0.251/252, 239.255.255.250), as apps used mDNS/LLMNR/SSDP again. So `after` is smaller because the table is soft state: it forgets, and is rebuilt only for neighbours I actually talk to.

**A4 · the far-away web server:** Not in the table, and it cannot be. ARP resolves an IP to a MAC **only on the same link/subnet**. For korea.ac.kr the next hop is the gateway, so the Ethernet destination is the gateway's MAC and the server's own IP is never ARPed (every router re-resolves its own next hop). The evidence is in my files: `arp-after.txt` has a single dynamic entry, the gateway, and the capture contains no request from my PC for any address except 192.168.0.1. The table is bounded by the number of *neighbours*, not by how much of the Internet I visit. ARP sits at the boundary between layer 3 and layer 2 and never crosses a router.

**B1 · request and reply:** Request = packet 9 (opcode 1), reply = packet 10 (opcode 2), 10 ms apart, so ARP finished in about the time of one round trip. (Packet 11 is an extra reply from 192.168.0.10 with no matching request in this capture; I cannot explain it from the capture alone.)

**B2 · destination MACs:** Request: **ff:ff:ff:ff:ff:ff** (broadcast). Reply: **4c:49:6c:11:94:f0**, the unicast MAC of my own NIC, i.e. the machine that asked. The request's ARP payload also carries Target MAC 00:00:00:00:00:00 (the thing being asked), which is a different field from the Ethernet destination.

**B3 · who received them:** The request was addressed to everyone, so **every station on the segment** received it and its network stack had to look at it. Only the owner of 192.168.0.1 answered. The reply went to **one station only, me**: the switch/AP could forward it to a single port because it had just learned my MAC from the source address of my request, which is Task 1's self-learning at work. The capture shows the broadcast side too: packets 34 and 35 are the gateway asking "who has 192.168.0.4?", a question about someone else that my PC still received. A question everybody must hear, an answer only one needs.

**B4 · ARP volume:** 35 ARP frames in 439 s, **about 4.8 per minute** (the busiest single minute, which contained my flush, had 9). Of these, only **3 were broadcasts (about 0.4 per minute)**. The other 30 are the gateway sending *unicast* requests to my PC every 27-40 s to re-check that I am still there, which only I see. Extrapolating, assuming every machine behaves like mine (a rough assumption from one quiet home network): a campus segment of N = 1000 machines would carry about 4,800 ARP frames a minute, and every machine would have to read about 400 broadcasts a minute from all the others. The total grows linearly with N, but each broadcast is processed by all N machines, so the work spent on reading them grows with N squared. That is the limit of ARP: it scales only because segments are kept small (VLANs, routed boundaries).

## Task 3 · A switch that runs out of room

**Eviction rule and evidence:** Evict the entry with the **lowest popularity count** (frequency-based, not arrival-based). Evidence: a bounded store of at most `4 × capacity` (256) counters, bumped when a station is heard from **or asked for** (a destination missing from the table is exactly what gets flooded). A newcomer replaces the least popular counter and starts at 1. Result: wasted 323,380 → **156,998 (−51 %, "strong")**, 0 missed. A fixed table holding the true top-64 would give −52.8 %, so little is left on the table. Other trace seeds give −49 % to −51 %.

**Declining admissions:** Yes. A newcomer enters a full table only if its count is *strictly greater* than the weakest entry's. On this trace it is worth little: the same counters with unconditional learning give −51.1 % vs −51.5 %. About 0.3 points here, and 0.2–0.5 on five other seeds. The big gain came from changing *what is evicted*, not from declining. A lesson from the counters: with the textbook Space-Saving rule (newcomer inherits the evicted count) a stream of forged one-off addresses inflates its own counts and 45 of them ended up in the table. Starting new counters at 1 cut that to 0 with the same −51.5 % on clean traffic. Declining never loses a delivery: a station not in the table is flooded and still receives its frame.

**R6 · the attack (MAC flooding / CAM-table overflow):** The attacker knows the table is small and that an unknown destination is flooded. So they send a stream of frames with random forged source MACs. Each one is learned, the real stations are pushed out, and from then on the switch floods their traffic out of *every* port, including the attacker's. The attacker can now read other people's unicast traffic (the switch has become a hub), and the flooding itself hurts every port. I simulated 5 forged sources per legitimate frame: legit-station waste rose ×3.3 on the FIFO baseline, and ×1.00 on mine, since one-shot addresses stay at count 1 and are declined. The limit: a patient attacker that *repeats* a pool of 60–200 forged MACs builds up real counts. Against that, my switch's waste rose ×2.2–4.8 relative to its own clean run (still below the baseline's absolute waste in all four cases I tried). A frequency policy only raises the price. **What a switch can do:** port security: cap the number of distinct source MACs per access port (a few, not 64), drop or shut the port on violation, and/or rate-limit new-MAC learning per port. That is an admission policy applied per port, so an attacker on one port can only ever occupy that port's quota.
